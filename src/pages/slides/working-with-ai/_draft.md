  - 0. LLM은 비결정적 도구 (약 10분)

    - '비결정성'은 같은 입력에도 출력이 달라질 수 있음을 말함
    - LLM의 비결정성은 추론 방식에서 옴

      - (장표는 매머드 도표로 My favourite colour is... 30% Red, 30% Green, 0.2% Trevor)
      - (추론으로 한 글자(토큰)씩 이어 붙임)
      - (다음 토큰마다 확률을 매기고, 그중 하나를 골라 반복)
      - (“정답 하나”를 조회하는 구조가 아니라 확률적으로 문장을 완성함)

    - (마음에 드는 문장이 나올 확률을 높이는 것이 실무진의 관심사)
    - (모델 크기·학습 과정·해석 연구는 생략)
    - (그래서 확률을 높이는 방법 세 가지: 작업 지침, 맥락 관리, 결정적 도구)

  - 1. 확률 높이기 (약 30분)

    - 작업 지침

      - ⭐️ 일을 잘하는 개발자
        - 지침은 일 잘하는 선배의 습관을 문서로 적어 둔 것
        - (신입에게 업무 매뉴얼을 주듯 AI에게도 일하는 방식을 알려 줌)
      - andrej-karpathy의 CLAUDE.md
        - 먼저 생각하기: 추측하지 말고, 헷갈리면 물어보기
        - 단순하게: 문제를 푸는 최소한의 코드
        - 필요한 곳만 고치기
        - 목표 기준 실행: 성공 기준을 먼저 정하고 통과할 때까지 반복
        - (Karpathy가 X에 올린 글을 Forrest Chang이 CLAUDE.md로 정리)
      - ponytail
        - YAGNI: 정말 필요한가?
        - 있는 도구 활용하기: 기존 코드 → 표준 기능 → 이미 설치된 도구 순서로 확인
        - (가장 게으른 시니어 개발자처럼 생각하게 만드는 지침)
      - caveman
        - 불필요한 조사 없애기: 인사말, 군더더기, 얼버무림 제거
        - 기술 용어와 코드는 그대로 유지
        - (토큰은 비용이자 맥락. 짧게 말할수록 둘 다 아낌)
      - i-have-adhd
        - 액션 아이템으로 안내하기: 다음 행동부터 말하기
        - 목록은 5개 이하, 서론·맺음말 없음
      - superpowers, mattpocock, ecc
        - 워크플로우 쪼개기
        - superpowers: 브레인스토밍 → 계획 → 테스트 먼저 → 하위 에이전트에 분배
        - mattpocock: grill-me, 추천 답과 함께 질문을 하나씩 던져 계획을 다듬음
        - ecc: 기획·테스트·리뷰 등 역할별 에이전트 팀
      - (무작정 설치하기 보다 지침의 원리를 파악하는 것이 중요)

    - 맥락 관리

      - context가 가득 차면 할루시네이션 발생 확률이 급증
        - (Chroma "Context Rot" 연구: 입력이 길어질수록 단순한 작업에서도 성능이 떨어짐)
        - (Anthropic: 가장 적은 수의, 신호가 높은 토큰을 넣는 것이 목표)
      - ⭐️ 점진적 공개
        - 목차만 먼저 → 필요할 때 본문 → 더 필요하면 부록
        - (책을 통째로 외우지 않고 목차를 보고 필요한 장만 펼치는 것과 같음)
        - (Agent Skills: 처음엔 이름과 설명만 읽고, 관련 작업일 때 본문과 파일을 읽음)
      - 문서화: 코딩 컨벤션, 의사 결정 문서, 기획·디자인 문서
      - 외부 연결: MCP, Open API
        - (MCP: AI가 외부 서비스에 접속하는 표준 플러그)

    - 결정적 도구

      - strawberry의 r은 몇 개?
        - (요즘은 모델 성능이 좋아서 올바르게 잘 대답하지만)
        - (텍스트를 확률 기반으로 생성하는 LLM 입장에서는 어려운 질문이었음)
        - r 개수를 세는 코드를 작성하고 실행하면 100% 정확
      - 정적분석: eslint, fallow, knip, react-doctor ...
        - (트리(AST) 기반으로 소스 코드를 분석해서 취약점을 찾음)
        - eslint: 정해 둔 규칙 위반 검사
        - knip, fallow: 안 쓰는 파일·코드·의존성 찾기
        - react-doctor: React 코드 건강 점수
        - (맞춤법 검사기처럼 코드를 실행하지 않고 읽기만 해서 문제를 찾음)
      - 테스팅: playwright
        - (브라우저를 대신 눌러 보는 로봇)
        - (TDD)
        - (채점 기준을 먼저 만들고 답안을 작성하는 방식)

    - (claude code, codex 가 이런 지침을 어느 정도 내장하고 있고 활발히 업데이트 되고 있음)
    - LLM을 넘어 AI 에이전트의 시대
      - 에이전트 = LLM + 지침 + 맥락 + 도구 + 반복 실행
      - (앞에서 본 작업 지침, 맥락 관리, 결정적 도구가 모두 에이전트 안에 들어 있음)
      - (챗봇은 답을 주고 끝나지만, 에이전트는 스스로 도구를 쓰고 결과를 확인하며 반복함)

  - 2. 워크플로우 자동화 (약 10분)

    - 내가 반복하는 작업을 AI가 수행
    - plan > implement > review > merge
      - (계획 → 구현 → 검토 → 반영. 사람의 업무 결재 흐름과 같음)
    - 단계마다 입력·결과물·완료 기준
      - plan: 기획서 → JIRA 티켓(티켓 설명 = 계획서). pyan-plan, uiop. 완료: 내가 승인
      - implement: 티켓 하나 → 코드. pyan-implement. 완료: 티켓 항목 완료 + lint·type·test 통과
      - review: 코드 → 지적 사항. lint·test, 모델 리뷰. 완료: 내가 최종 검토
      - merge: 코드 → 커밋·PR. pyan-commit, pyan-write-pr. 완료: 동료 승인 후 내가 머지
      - (티켓 하나 = PR 하나)
      - (계획 승인, 최종 검토, 머지 결정은 사람이 함. 빙산 아래의 검증)
    - 오픈소스보다 나의 워크플로우를 정의하기
      - 단계: 매번 같은 순서로 하는 일을 나누기
      - 입력·결과물: 각 단계가 무엇을 받아 무엇을 넘기는지
      - 완료 기준: 언제 다음 단계로 넘어가는지, 누가 판단하는지
      - (남이 만든 흐름은 우리 팀의 티켓·리뷰 순서까지 알 수 없음)
      - (논문 리뷰, 실험 결과 정리처럼 매번 같은 순서로 하는 일을 먼저 글로 적어 보기)

  - 3. 직군 간의 경계 허물기 (약 10분)

    - 가장 큰 비용은 커뮤니케이션
      - 개발자는 생각보다 코딩할 시간이 별로 없음
      - 비개발자와의 커뮤니케이션: 기획, 디자인, 외부 부서
      - 개발자 간의 커뮤니케이션: 동일 직군, 다른 직군
    - => 진정한 AI의 혁신
      - 사람 간 커뮤니케이션을 없애는 것
      - 지금: 기획자 A → 기획자 B → 개발자 A → 개발자 B → … → 의사결정
      - 앞으로: 기획자 A → AI → 의사결정
      - 그래서 맥락을 AI가 읽을 수 있는 곳으로 옮기는 중
      - (회의록, 기획서, 디자인 파일이 AI가 읽을 수 있는 곳에 있어야 함)
    - 사례: 당근, 배포 내역을 누구나 물어볼 수 있게
      - 문제: "이 기능 언제 나갔어요?"마다 개발자가 기록을 뒤짐
      - 한 일: 배포 내역을 Notion에 쌓고, AI가 비개발자도 읽는 릴리즈 노트로 번역
      - 결과: 위클리 정리를 자동 노트로 대체, 다른 팀도 요청해 주간 요약 추가
    - 사례: 배달의민족, 흩어진 사내 지식을 에이전트 하나로
      - 문제: 정보가 흩어져 있어 질문마다 각 시스템을 일일이 찾아다님
      - 한 일: 위키, Jira, Slack, 구글 드라이브를 AI 에이전트 물어보새에 연결
      - 결과: 전 직원 33% 사용, 조직별 문의 해결 속도 평균 21% 향상 (기사 기준)
    - 사례: 토스, 분석가를 기다리지 않는 데이터 조회
      - 문제: 분석가에게 오는 요청의 70%가 단순 수치 추출
      - 한 일: 테이블 설명, 용어, 지표 정의를 AI가 읽게 먼저 정리하고 데이터봇 판다 제작
      - 결과: 출시 첫 주 팀원 절반, 현재 70%가 사용
    - 사례: Uber, 온콜 엔지니어를 기다리지 않는 사내 질문
      - 문제: 지원 채널에 월 약 45,000건의 질문, 답은 온콜 엔지니어를 기다려야 함
      - 한 일: 사내 위키, 사내 Q&A, 요구사항 문서를 AI 봇 Genie에 연결
      - 결과: 154개 채널에서 7만 건 이상 답변, 엔지니어링 13,000시간 절약(추정)
      - (네 회사 모두 AI보다 맥락을 먼저 옮김)

  - AI는 비결정적이다. 원하는 결과가 나올 확률을 높이는 구조를 만든다
    - 작업 지침, 맥락 관리, 결정적 도구

    - plan > implement > review > merge

  - 예시 2: add-matrix
    - 문제: 앱마다 에러 모니터링(Matrix) 설정을 반복. 4개 환경 앱 생성, env 파일, Sentry 연동, 알림 정책까지 여러 사내 도구를 오가는 수작업
    - 워크플로우: SKILL.md에 단계 정의 > 단계마다 스크립트로 API 호출 > env와 API 응답으로 검증 > 사람 손이 필요한 일만 안내
    - 결과: 대화 한 번으로 설정 완료. 누가 실행해도 같은 결과
    - 사용 개념: 작업 지침, 맥락 관리, 결정적 도구
    - (슬라이드에서 데모)
  - 예시 3: pyan-tldr
    - 문제: 읽어야 할 정보가 너무 많음
    - 워크플로우: 정보 수집 (cli로 유튜브, 네이버 블로그 콘텐츠 탐색 > tldr 프롬프트로 정보 요약)
    - 결과: 30분 동안 훑어야 할 정보를 1분 안에 파악하고 문서로 정리
    - 사용 개념: 작업 지침, 결정적 도구
