## LLM은 비결정적 도구 (약 10분)

### #7 LLM은 비결정적 도구

가장 먼저 알아야 할 사실은 LLM이 비결정적 도구라는 점이에요. 비결정성은 같은 입력을 넣어도 출력이 달라질 수 있다는 뜻입니다.

화면 아래를 보시면, 계산기는 결정적 도구예요. 2 더하기 3을 백 번 눌러도 매번 5가 나옵니다. 그런데 ChatGPT에 같은 질문을 두 번 해 보시면 대답이 조금씩 달라요. 표현이 바뀌기도 하고, 가끔은 내용이 바뀌기도 합니다.

[질문] 같은 질문을 했는데 답이 달라서 당황했던 경험 있으신 분 계신가요?

[데모] 새 대화 두 개에 "AI로 일하는 법을 한 문장으로 알려 줘"를 똑같이 넣고, 두 답을 나란히 보여 준다.

보시는 것처럼 질문은 글자 하나 다르지 않은데 답이 다릅니다. 왜 이런 일이 생기는지 보겠습니다.

### #8 My favorite color is \_\_\_

이 비결정성은 LLM이 문장을 만드는 방식에서 옵니다.

LLM은 글을 한 번에 쓰지 않아요. 한 글자씩, 정확히는 토큰이라는 조각 단위로 이어 붙입니다. "My favorite color is" 다음에 무엇이 올지 모든 후보에 확률을 매겨요. Red가 30%, Green이 30%, 그리고 아주 낮지만 Trevor 같은 엉뚱한 단어도 0.2% 정도 확률을 가집니다.

그중 하나를 고르고, 고른 단어를 붙인 다음 다시 다음 토큰의 확률을 매기고, 이걸 반복합니다. 그러니까 LLM은 데이터베이스처럼 정답 하나를 조회하는 구조가 아니에요. 확률적으로 문장을 완성해 가는 구조입니다. 오늘 Red가 나왔다고 내일도 Red가 나온다는 보장이 없는 거죠.

그래서 실무자들의 관심사는 하나로 모입니다. 마음에 드는 문장이 나올 확률을 어떻게 높일 것인가.

모델 크기, 학습 과정, 내부를 해석하는 연구도 흥미로운 주제지만 오늘은 생략할게요. 대신 확률을 높이는 방법 세 가지로 넘어가겠습니다. 작업 지침, 맥락 관리, 결정적 도구입니다.

## 확률 높이기 (약 30분)

### #9 확률 높이기

화면에 세 가지가 있습니다. 작업 지침은 AI에게 일하는 방식을 알려 주는 것, 맥락 관리는 AI가 보는 정보를 잘 고르는 것, 결정적 도구는 확률에 맡기면 안 되는 일을 확실한 도구에 넘기는 것이에요. 하나씩 보겠습니다.

### #10 1. 작업 지침

첫 번째는 작업 지침입니다.

### #11 일을 잘하는 개발자

작업 지침의 핵심은 이 한 줄입니다. 지침은 일 잘하는 선배의 습관을 문서로 적어 둔 것이에요.

회사에 신입이 들어오면 업무 매뉴얼을 주잖아요. "보고서는 이 양식으로 써라", "모르면 추측하지 말고 물어봐라" 같은 것들이요. AI에게도 똑같이 일하는 방식을 알려 줄 수 있습니다. Claude Code에서는 CLAUDE.md라는 파일에 이런 지침을 적어 두면 AI가 매번 읽고 따라요.

지금부터 개발자들 사이에서 널리 쓰이는 지침 몇 가지를 보여 드릴 텐데, 도구 이름보다는 각 지침이 어떤 습관을 담고 있는지에 집중해 주세요.

### #12 andrej-karpathy의 CLAUDE.md

Andrej Karpathy는 OpenAI 창립 멤버이자 테슬라 AI 총괄을 지낸 사람이에요. 이 사람이 X에 "AI 코딩 도구가 자주 저지르는 실수"에 대한 글을 올렸고, Forrest Chang이라는 개발자가 그 내용을 CLAUDE.md 파일로 정리했습니다.

원래 원칙은 네 가지인데, 화면에서는 비슷한 두 개를 묶었어요. 먼저 생각하기: 추측하지 말고, 헷갈리면 물어보기. 단순하게: 문제를 푸는 최소한의 코드만 쓰기. 여기에 필요한 곳만 고치기가 붙어요. 부탁하지 않은 부분은 건드리지 않는 거죠. 마지막으로 목표 기준 실행: "잘 되게 해 줘"가 아니라 "이 검사를 통과하게 해 줘"처럼 확인할 수 있는 기준을 먼저 정하고, 통과할 때까지 반복합니다.

읽어 보시면 AI 전용 규칙이라기보다 좋은 동료의 조건에 가깝죠. 사실 제가 쓰는 설정 파일에도 이 원칙이 거의 그대로 들어 있습니다.

### #13 ponytail

ponytail은 "방에서 가장 게으른 시니어 개발자처럼 생각하게 만드는" 지침이에요. 슬로건이 "가장 좋은 코드는 쓰지 않은 코드"입니다. 코드는 쓰는 순간부터 고치고 관리해야 할 짐이 되거든요.

그래서 먼저 YAGNI를 묻습니다. You Aren't Gonna Need It, 즉 "정말 필요한가?"를 먼저 묻는 거예요. AI는 시키지 않은 기능까지 만들어 주려는 경향이 있거든요.

필요하다면 새로 만들기 전에 순서대로 확인합니다. 이미 있는 코드로 되는지, 표준 기능으로 되는지, 이미 설치된 도구로 되는지. 예를 들어 날짜 선택 기능이 필요하면 무거운 외부 도구를 들이기 전에 브라우저에 기본으로 있는 날짜 입력칸부터 써 보는 식이에요. 이 순서를 다 거쳐도 안 될 때만 새로 만듭니다.

### #14 caveman

caveman은 이름 그대로 원시인처럼 말하게 하는 지침입니다. 소개 문구가 "why use many token when few token do trick"인데, 문법까지 일부러 원시인처럼 써 놨어요. 적은 토큰으로 같은 내용을 전달하자는 거죠.

"물론이죠! 좋은 질문입니다" 같은 인사말, "사실", "기본적으로" 같은 군더더기, "아마도 그럴 수도 있습니다" 같은 얼버무림을 뺍니다. 대신 기술 용어, 코드, 에러 메시지는 한 글자도 바꾸지 않아요. 정확해야 하는 부분까지 줄이면 안 되니까요.

왜 이게 중요하냐면, AI에게 토큰은 비용이자 맥락이기 때문이에요. 쓸데없는 말이 길어질수록 돈도 들고, AI가 기억할 수 있는 공간도 차지합니다. 짧게 말할수록 둘 다 아낄 수 있어요.

### #15 워크플로우 쪼개기

앞의 지침들이 "어떻게 말하고 행동할지"였다면, 이번 것들은 "일을 어떤 순서로 할지"예요.

superpowers는 브레인스토밍, 계획, 테스트 먼저 작성, 하위 에이전트 실행으로 이어지는 흐름을 강제합니다. 계획은 2~5분짜리 작은 일로 쪼개고, 하위 에이전트가 일을 하나 끝낼 때마다 리뷰를 거쳐요.

mattpocock의 grill-me는 AI가 계획의 모든 갈래를 따라가며 질문을 하나씩 던지는데, 질문마다 자기 추천 답을 붙입니다. 사실 오늘 강의안도 이 방식으로 AI와 질문을 주고받으며 다듬었어요.

ecc는 메인 AI가 PM 역할만 하고, 실제 작업은 기획, 테스트, 리뷰 같은 역할별 하위 에이전트가 맡는 구조예요. 회사의 팀 구성과 비슷하죠.

공통점은 큰 일을 작은 단계로 쪼갠다는 겁니다. 한 번에 다 시키면 확률이 낮지만, 단계를 나누면 각 단계의 성공 확률이 높아지거든요.

### #16 skills.sh

지금까지 소개한 지침들은 어디서 찾을까요. skills.sh는 AI 에이전트용 스킬을 모아 둔 공개 디렉터리예요. 명령어 한 줄로 내 AI 도구에 설치할 수 있습니다.

[이미지] 오른쪽 순위표를 보시면 앞에서 소개한 mattpocock의 grill-me가 2위에 있어요. 설치 수가 130만이 넘습니다. 그만큼 많은 사람이 남이 만든 일하는 방식을 가져다 쓰고 있다는 뜻이에요.

여기서 몇 가지만 더 소개할게요.

i-have-adhd는 답을 파묻지 않게 하는 지침이에요. AI에게 물어보면 서론이 길고 정작 할 일은 맨 아래에 있을 때가 많죠. 이 지침은 다음 행동부터 말하게 하고, 여러 단계라면 번호를 매겨 지금 어디쯤인지 매번 알려 주게 합니다. 서론과 맺음말은 빼고, 목록은 5개를 넘기지 않아요.

eli5는 Explain Like I'm 5, "다섯 살에게 설명하듯"이라는 뜻이에요. 듣는 사람을 먼저 정하고 그 수준에 맞춰 설명하게 합니다. 나이, 학력, 직무별로 설명 방식이 표로 정리돼 있는데, 대학원생 항목도 있어요. 대학원생에게는 기초는 안다고 보고 미묘한 차이와 한계에 집중하라고 되어 있습니다. 오늘 강의 내용을 동료에게 설명할 때 써 보셔도 좋아요.

modern-web-guidance는 구글 크롬 팀이, react-best-practices는 Vercel이 만든 스킬이에요. AI는 오래된 코드를 많이 학습해서 옛날 방식으로 코드를 짜는 경향이 있거든요. 이 스킬들은 최신 웹 기능과 모범 사례를 필요할 때만 꺼내 AI의 맥락에 넣어 줍니다. react-best-practices는 70개 규칙을 영향이 큰 순서로 8개 분류에 정리해 뒀어요. 필요한 것만 그때 읽는다는 점에서, 뒤에서 볼 맥락 관리와도 이어집니다.

여기서 꼭 드리고 싶은 말이 있어요. 이런 지침은 무작정 설치하기보다 원리를 파악하는 게 중요합니다. 남의 습관을 통째로 가져오면 내 일에 맞지 않는 부분이 생겨요. 왜 이런 규칙이 생겼는지 이해하면 내 상황에 맞게 골라 쓸 수 있습니다.

### #17 2. 맥락 관리

두 번째는 맥락 관리입니다.

### #18 context가 가득 차면 할루시네이션 발생 확률이 급증

AI가 한 번에 볼 수 있는 정보의 양을 context라고 해요. 대화가 길어지거나 자료를 너무 많이 넣으면 이 공간이 가득 차는데, 그러면 할루시네이션, 즉 그럴듯한 거짓말이 나올 확률이 급격히 올라갑니다.

Chroma라는 회사가 여러 모델을 실험한 "Context Rot" 연구를 보면, 입력이 길어질수록 아주 단순한 작업에서도 성능이 떨어졌어요.

[그래프] 가로축은 입력 길이, 세로축은 정확도예요. 긴 논문 더미 속에서 특정 문장을 찾아내는 실험인데, 오른쪽으로 갈수록, 즉 입력이 길어질수록 선이 내려갑니다. 특히 빨간 선은 질문과 정답 문장의 표현이 서로 덜 비슷한 경우인데, 입력이 10만 토큰을 넘어가면 정확도가 절반 아래로 떨어지기도 해요. 실제로 우리가 던지는 질문도 정답 문장과 표현이 똑같지 않은 경우가 많죠. Anthropic도 비슷한 이야기를 합니다. 목표는 가장 적은 수의, 신호가 높은 정보만 넣는 것이라고요.

많이 넣을수록 좋은 게 아니라, 필요한 것만 골라 넣어야 합니다.

### #19 점진적 공개

맥락 관리의 핵심 개념은 점진적 공개예요.

두꺼운 전공 서적을 공부할 때 처음부터 끝까지 외우지 않잖아요. 목차를 먼저 보고, 필요한 장을 펼치고, 더 필요하면 부록을 찾아봅니다. AI에게도 똑같이 정보를 줍니다. 목차만 먼저, 필요할 때 본문, 더 필요하면 부록.

실제로 Claude의 Agent Skills가 이렇게 동작해요. 다음 장에서 실제 스킬 폴더로 보여 드릴게요.

### #20 예시: Agent Skill 폴더

실제 스킬 폴더는 이렇게 생겼어요. 사실 오늘 이 발표 자료도 frontend-slides라는 스킬로 만들었습니다.

맨 위의 name과 description이 목차예요. AI는 대화를 시작할 때 이 두 줄만 읽어 둡니다. 제가 "발표 자료 만들어 줘"라고 하면 그때 SKILL.md 본문을 펼쳐서 만드는 순서를 읽어요. 그리고 스타일을 고르는 단계가 되어서야 STYLE_PRESETS.md를, 실제 코드를 쓰는 단계가 되어서야 viewport-base.css를 엽니다.

필요한 순간에 필요한 만큼만 읽으니까, 이런 스킬이 수십 개 있어도 context가 가득 차지 않아요.

### #21 맥락은 어디서 오나

그럼 AI에게 줄 맥락은 어디서 올까요.

첫째는 문서화예요. 코딩 컨벤션, 왜 이렇게 결정했는지 적은 의사 결정 문서, 기획서와 디자인 문서 같은 것들이요. 사람 머릿속에만 있는 정보는 AI가 읽을 수 없습니다.

둘째는 외부 연결이에요. MCP는 AI가 외부 서비스에 접속하는 표준 플러그라고 생각하시면 됩니다. 콘센트 모양이 통일되어 있으면 어떤 가전이든 꽂을 수 있듯이, MCP로 연결하면 AI가 캘린더, 문서, 이슈 관리 도구 같은 곳의 정보를 직접 가져올 수 있어요. Open API도 같은 역할을 합니다.

[코드 블록] 예시로 mattpocock의 setup-matt-pocock-skills라는 스킬을 가져왔어요. 이 스킬을 한 번 돌리면 이런 문서 자리를 잡아 주고, 같은 모음의 다른 스킬들은 모두 여기를 읽고 씁니다.

맨 위 CLAUDE.md는 이정표예요. 여기에는 "이슈는 어디서 관리하고, 도메인 문서는 어디 있다"는 한 줄짜리 안내만 적고, 자세한 내용은 docs/agents 아래 파일로 넘깁니다. issue-tracker.md에는 이슈를 GitHub에서 관리하는지 로컬 파일로 관리하는지를, domain.md에는 "작업 전에 용어집과 결정 기록부터 읽어라" 같은 읽는 규칙을 적어요. AI는 이정표만 읽고 있다가 필요할 때 그 파일을 펼칩니다. 점진적 공개 그대로죠.

GLOSSARY.md는 용어집이에요. 팀에서 쓰는 단어 하나마다 정의를 적고, "이 말은 쓰지 말 것"까지 적습니다. 같은 걸 누구는 회원, 누구는 유저라고 부르면 AI도 헷갈리거든요. AI가 이슈 제목이나 테스트 이름을 지을 때도 여기 있는 단어를 씁니다.

docs/adr는 결정 기록이에요. 결정 하나당 파일 하나를 번호를 붙여 남깁니다. 로그인은 OAuth로 한다, 세션은 DB 대신 Redis에 둔다, 서비스는 아직 쪼개지 않는다. 이런 결정마다 그때의 상황과 이유를 적어 둬요. 이게 없으면 AI는 "서비스를 분리하면 좋겠어요" 같은 제안을 틈날 때마다 다시 꺼냅니다. 그래서 이 스킬 모음은 AI가 코드 구조 개선을 제안했다가 제가 "이건 이런 이유로 안 된다"고 거절하면, 그 이유를 결정 기록으로 남길지 먼저 물어봐요.

그리고 이 두 파일은 처음부터 채워 두지 않아요. 대화하다가 용어가 정리되거나 결정이 내려지는 순간에 그때그때 만들어집니다. 문서화할 시간을 따로 내지 않아도 작업하면서 쌓이는 셈이에요.

마지막 .mcp.json은 문서는 아니지만, AI가 접속할 외부 서비스를 적어 두는 곳입니다.

### #22 맥락은 어디서 오나

[코드 블록] 두 번째 예시는 앞에서 본 superpowers 워크플로우가 남기는 문서예요. 두 파일 모두 이름에 날짜가 들어가 있어서 언제 무엇을 정했는지 따라갈 수 있습니다.

specs는 브레인스토밍 스킬이 쓰는 설계 문서예요. AI가 질문을 하나씩 던지고, 방법 두세 가지를 장단점과 함께 제안하고, 제가 고른 설계를 아키텍처, 구성 요소, 데이터 흐름, 오류 처리, 테스트 순서로 적습니다. 다 쓰고 나면 AI가 스스로 한 번 더 읽으면서 "나중에 정함" 같은 빈칸이 없는지, 앞뒤가 모순되지 않는지, 두 가지로 읽힐 문장이 없는지 고쳐요. 참고로 작은 작업이면 문서를 만들지 않고 대화로 끝냅니다. 문서는 구조를 바꾸는 큰 작업에만 남겨요.

plans는 그 설계를 실행 계획으로 쪼갠 문서예요. 스킬 지침 첫 줄이 "이 코드베이스도, 이 설계도 본 적 없는 엔지니어를 위해 써라"입니다. 그래서 맨 위에 한 문장 목표와 접근 방식, 따라야 할 설계 문서, 버전이나 의존성 같은 전체 제약을 먼저 적어요.

그 아래는 작업 단위예요. 작업마다 만들고 고칠 파일을 정확한 경로로 적고, 앞 작업에서 받을 것과 뒤 작업에 넘길 것을 함수 이름과 타입까지 적습니다. 작업 하나를 맡은 AI는 자기 작업만 보기 때문에, 이 칸이 옆 작업과 이름을 맞추는 유일한 통로예요. 마지막은 체크박스 단계인데, 실패하는 테스트 쓰기, 실패 확인, 구현, 통과 확인, 커밋 순서로 한 단계에 한 동작씩 적어요.

연구로 바꿔 보면 이렇습니다. 용어집은 논문의 용어 정의, 결정 기록은 "이 방법을 왜 택했는지" 적어 둔 연구 노트, specs와 plans는 실험 설계와 실험 절차예요.

정답은 없습니다. 여러분의 자료가 어디에 쌓이는지, 즉 연구 노트인지, 공유 드라이브인지, 메신저인지 먼저 보고, AI가 거기에 닿을 수 있게 만드는 게 출발점이에요.

### #23 3. 결정적 도구

세 번째는 결정적 도구예요.

### #24 strawberry의 r은 몇 개?

퀴즈 하나 내 볼게요.

[질문] strawberry에 r은 몇 개일까요?

[데모] 같은 질문을 AI에게 해 본다. 맞게 답하면 아래 설명으로 넘어가고, 틀리면 그 자체를 보여 준다.

세 개죠. 요즘 모델은 성능이 좋아서 대부분 올바르게 대답합니다. 그런데 불과 얼마 전까지만 해도 AI가 이 질문에 두 개라고 틀리게 답하는 걸로 유명했어요.

앞에서 LLM은 토큰 단위로 확률을 계산한다고 했죠. strawberry라는 단어는 글자 하나하나가 아니라 몇 개의 덩어리로 보이기 때문에, 글자 수를 세는 건 LLM 입장에서 의외로 어려운 문제였습니다.

해결책은 간단합니다. 세는 코드를 작성하고 실행하면 돼요. 화면의 코드는 strawberry에서 r이 몇 번 나오는지 세는 한 줄짜리 코드입니다.

[데모] 같은 대화에서 "코드로 세어 줘"라고 요청해, AI가 코드를 쓰고 실행하는 모습을 보여 준다.

이렇게 하면 100% 정확해요. 확률이 아니라 계산이니까요.

여러분도 AI에게 통계값이나 합계를 물어볼 때 "코드로 계산해서 알려 줘"라고 요청해 보세요. 확률에 맡길 일과 계산에 맡길 일을 구분하는 것, 이게 결정적 도구의 핵심입니다.

### #25 정적분석

개발자들은 이런 결정적 도구를 적극적으로 씁니다. 대표적인 게 정적분석이에요.

정적분석은 맞춤법 검사기와 비슷합니다. 코드를 실행하지 않고 읽기만 해서 문제를 찾아요. 코드를 나무 구조로 분해한 다음, 규칙에 어긋나는 곳이나 취약한 곳을 찾아냅니다.

eslint는 정해 둔 규칙을 어겼는지 검사하고, knip과 fallow는 쓰지 않는 파일이나 코드를 찾아 줘요. react-doctor는 React 코드의 건강 점수를 매겨 줍니다. AI가 코드를 쓰면 이런 도구가 자동으로 검사하고, 문제가 있으면 AI가 스스로 고치게 해요.

### #26 테스팅

또 하나는 테스트입니다. 테스트는 확인하는 범위에 따라 크게 세 가지로 나눠요.

e2e는 End to End, 처음부터 끝까지라는 뜻이에요. 실제 사용자처럼 사이트에 들어가서 버튼을 누르고 결과 화면까지 확인합니다. integration은 여러 부분을 이어 붙였을 때 함께 잘 돌아가는지 봐요. 예를 들어 로그인 화면과 회원 정보 서버가 서로 잘 주고받는지요. unit은 가장 작은 단위로, 함수 하나가 맞는 값을 돌려주는지 봅니다.

자동차에 비유하면 unit은 부품 하나하나 검사, integration은 엔진과 변속기를 이어서 검사, e2e는 실제로 도로를 달려 보는 시험 주행이에요. 작은 테스트일수록 빠르고 많이 돌릴 수 있고, 큰 테스트일수록 느리지만 실제 사용자 경험에 가깝습니다.

e2e 테스트를 대표하는 도구가 playwright예요. 브라우저를 대신 눌러 보는 로봇이라고 생각하시면 됩니다.

[이미지] 왼쪽은 테스트 목록이고, 가운데는 로봇이 한 동작을 순서대로 적은 기록이에요. 페이지로 이동하고, "Get started" 링크를 누르고, "Installation" 제목이 보이는지 확인합니다. 오른쪽에는 그 순간의 실제 화면이, 아래에는 그 동작을 시킨 코드가 나와요. 빨간 점이 로봇이 누른 위치입니다. 전부 통과해서 초록색 체크가 떠 있죠.

개발자들은 TDD, 테스트 주도 개발이라는 방식을 쓰기도 해요. 채점 기준을 먼저 만들고 답안을 작성하는 방식입니다. AI에게 "이 테스트를 통과할 때까지 고쳐 줘"라고 하면, AI는 확률적으로 코드를 쓰더라도 결과는 테스트라는 결정적인 기준으로 판정돼요.

사실 Claude Code나 Codex 같은 도구는 지금까지 말씀드린 지침들을 어느 정도 이미 내장하고 있고, 아주 빠르게 업데이트되고 있습니다.

### #27 LLM을 넘어 AI 에이전트의 시대

그래서 이제는 LLM을 넘어 AI 에이전트의 시대라고 부릅니다.

에이전트는 LLM에 지침, 맥락, 도구, 그리고 반복 실행을 더한 거예요. 앞에서 본 작업 지침, 맥락 관리, 결정적 도구가 전부 에이전트 안에 들어 있습니다.

차이를 비유하면 이래요. 챗봇은 질문하면 답을 주고 끝납니다. 에이전트는 스스로 도구를 쓰고, 결과를 확인하고, 틀렸으면 다시 시도해요. 조언만 해 주는 사람과 직접 일을 처리해 주는 사람의 차이입니다.

에이전트가 스스로 일할 수 있게 되면서 할 수 있는 게 생겼어요. 내가 반복하는 작업을 AI에게 맡기는 겁니다.

### #30 워크플로우와 에이전트

Anthropic은 AI 시스템을 두 가지로 나눠요. 워크플로우는 사람이 경로를 미리 정해 두고, AI와 도구가 그 길을 따라가는 방식이에요. 에이전트는 AI가 어떤 순서로 무슨 도구를 쓸지 스스로 정합니다.

에이전트가 더 똑똑해 보이지만, 앞에서 본 것처럼 AI는 비결정적이에요. 매번 길을 새로 찾게 하면 결과도 매번 달라집니다. 그래서 반복하는 일일수록 경로를 먼저 정해 두는 게 좋아요. Anthropic도 가장 단순한 방법부터 쓰고, 필요할 때만 복잡하게 만들라고 합니다.

### #31 기본 패턴 5가지

같은 글에서 자주 쓰는 워크플로우 패턴 다섯 가지를 소개해요. 가운데 열은 글에 나온 예시이고, 오른쪽 열은 연구 상황으로 바꿔 본 거예요.

체이닝은 앞 단계 결과를 다음 단계 입력으로 넘기는 거예요. 목차를 쓰고, 목차가 기준에 맞는지 확인한 다음 본문을 쓰는 식이죠. 단계 사이에 확인을 끼워 넣을 수 있다는 게 장점이에요.

라우팅은 입력을 먼저 분류해서 알맞은 담당에게 보내요. 고객 문의를 환불과 기술 지원으로 나누듯, 논문 분야에 따라 다른 리뷰 기준을 쓰는 거예요.

병렬화는 여러 AI를 동시에 돌리고 결과를 모아요. 같은 문헌을 세 번 요약해서 세 번 모두 나온 내용만 믿으면, 한 번 요약할 때보다 틀릴 확률이 줄겠죠. 비결정성을 여러 번 시도해서 줄이는 방법이에요.

오케스트레이터와 워커는 팀장 AI가 일을 나눠 팀원 AI에게 맡기고 결과를 합칩니다. 지도교수가 문헌 조사를 주제별로 나눠 맡기고 취합하는 모습과 비슷해요. 체이닝과 다른 점은 어떻게 나눌지를 미리 정하지 않고 팀장 AI가 그때그때 정한다는 거예요.

평가자와 개선자는 한 AI가 쓰고 다른 AI가 첨삭하기를 반복해요. 초록을 쓰고 리뷰어 입장에서 고치기를 몇 번 되풀이하는 거죠.

앞에서 소개한 superpowers도 뜯어보면 이 패턴의 조합이에요. 브레인스토밍, 계획, 구현으로 이어지는 흐름은 체이닝이고, 하위 에이전트에게 작업을 나눠 주는 건 오케스트레이터와 워커, 구현 뒤의 리뷰는 평가자와 개선자입니다.

### #32 예시: 탐색 → 계획 → 구현 → 커밋

여기부터는 실제로 쓰이는 워크플로우 예시예요. 먼저 Claude Code 공식 문서가 권하는 기본 흐름입니다.

탐색 단계에서는 AI가 코드를 읽기만 하고 아무것도 고치지 않아요. 계획 단계에서는 어떤 파일을 바꾸고 흐름이 어떻게 되는지 정리하고, 사람이 그 계획을 직접 고칠 수 있어요. 구현 단계에서 코드를 쓰고 테스트를 돌리고, 마지막에 커밋과 PR까지 맡깁니다.

핵심은 탐색과 구현을 떼어 놓는 거예요. 바로 코드부터 쓰게 하면 엉뚱한 문제를 풀 수 있거든요.

[강조] 그렇다고 모든 일에 계획을 세울 필요는 없어요. 공식 문서 기준은 이래요. 바뀔 내용을 한 문장으로 설명할 수 있으면 계획은 건너뛴다. 오타 하나 고치는 데 계획서를 쓰는 건 낭비입니다.

같은 문서에서 가장 먼저 강조하는 건 검증이에요. 테스트, 빌드, 스크린샷처럼 AI가 직접 돌려 보고 통과했는지 알 수 있는 수단을 주라고 합니다. 그게 없으면 사람이 매번 검사관이 되어야 해요.

### #33 예시: 명세 주도 개발

GitHub이 만든 spec-kit은 명세 주도 개발이라는 흐름을 제안해요. "어떻게"를 정하기 전에 "무엇을, 왜"를 먼저 정하자는 겁니다.

constitution은 프로젝트 원칙이에요. 코드 품질, 테스트 같은 기준을 처음에 한 번만 씁니다. 그다음 기능마다 specify로 무엇을 왜 만드는지, plan으로 어떤 기술과 구조로 만들지, tasks로 실행할 작업 목록을 차례로 만들어요.

마지막 implement와 converge는 한 쌍이에요. 구현한 다음 명세와 맞는지 확인하고, 안 맞으면 다시 구현합니다. 명세가 완료 기준 역할을 하는 셈이죠.

연구로 치면 연구 계획서를 먼저 쓰고 실험하는 것과 같아요. 결과가 계획서의 가설을 검증할 때까지 실험을 반복하는 거죠.

### #34 예시: 반복, 분리, 팬아웃

마지막은 조금 더 과감한 예시 세 가지예요.

첫 번째는 될 때까지 반복하는 방법이에요. Geoffrey Huntley라는 개발자가 소개했고, 만화 캐릭터 이름을 따서 Ralph라고 부릅니다. 아래 코드 한 줄이 전부예요. 할 일을 적은 지시서 한 장을 AI에게 주고, 끝나면 같은 지시서를 또 주고, 또 줍니다.

그냥 반복만 하면 엉망이 되겠죠. 그래서 규칙이 두 개 있어요. 한 번에 한 가지만 한다. 그리고 채점을 통과해야 다음으로 넘어간다. 문제집을 풀 때 한 문제 풀고 답을 맞춰 보고, 맞아야 다음 문제로 넘어가는 것과 같아요. 여기서 채점은 앞에서 본 결정적 도구, 즉 사람이 아니라 프로그램이 맞고 틀림을 판정하는 검사입니다. AI가 가끔 틀려도 채점에서 걸러지니까, 반복할수록 결국 맞는 방향으로 모여요.

작성자와 검토자 분리는 코드를 쓴 세션과 검토하는 세션을 나누는 거예요. 새 세션은 방금 자기가 쓴 코드가 아니니까 편들지 않고 볼 수 있어요. 자기 논문의 오타가 자기 눈에는 잘 안 보이는 것과 같습니다.

팬아웃은 같은 일을 대량으로 할 때 써요. 공식 문서 예시는 파이썬 파일 2,000개를 새 버전으로 옮기는 작업이에요. 먼저 대상 파일 목록을 만들고, 파일마다 AI를 따로 실행합니다. 처음 두세 개로 프롬프트를 다듬은 다음 전체를 돌리라고 해요.

### #35 오픈소스보다 나의 워크플로우를 정의하기

중요한 건 오픈소스를 가져다 쓰기보다 나의 워크플로우를 정의하는 거예요. 앞에서 여러 워크플로우를 소개했지만, 제 업무에는 JIRA 티켓과 동료 리뷰가 있고 그 순서는 저희 팀만의 것이죠. 남이 만든 흐름은 거기까지 알 수 없습니다.

정의할 건 세 가지예요. 단계, 각 단계의 입력과 결과물, 완료 기준. 완료 기준에는 누가 판단하는지까지 적어 두세요. 이 세 가지가 정해지면 반복 업무를 맡기기 쉬워지고, 결과가 이상할 때 어느 단계에서 틀렸는지도 찾기 쉬워집니다.

여러분도 논문 리뷰, 실험 결과 정리처럼 매번 같은 순서로 하는 일이 있다면 그 순서를 먼저 글로 적어 보세요.

## 직군 간의 경계 허물기 (약 10분)

### #36 직군 간의 경계 허물기

### #37 가장 큰 비용은 커뮤니케이션

현업에서 가장 큰 비용은 커뮤니케이션이에요.

개발자는 하루 종일 코딩만 할 것 같지만, 실제로는 코딩할 시간이 생각보다 별로 없습니다. 기획자, 디자이너, 외부 부서 같은 비개발자와 이야기하고, 같은 개발자끼리도 서로 다른 영역을 맞추느라 시간을 많이 써요.

[질문] 여러분도 연구실에서 교수님이나 동료와 의견을 맞추는 데 쓰는 시간, 적지 않죠?

### #38 진정한 AI의 혁신

저는 사람과 사람 사이의 커뮤니케이션을 없애는 게 진정한 AI의 혁신이라고 생각합니다.

지금은 기획자 A가 궁금한 게 생기면 기획자 B에게 묻고, 기획자 B는 개발자 A에게, 개발자 A는 다시 개발자 B에게 물어요. 이렇게 몇 사람을 거쳐야 겨우 의사결정을 할 수 있습니다. 사람이 하나 늘 때마다 기다리는 시간이 생기고, 전달하면서 내용이 조금씩 달라지기도 해요.

맥락이 잘 정리되어 있다면 기획자 A가 AI에게 바로 묻고, 그 답으로 의사결정을 할 수 있습니다. 중간 단계가 전부 사라지는 거죠.

이렇게 하려면 회의록, 기획서, 디자인 파일이 AI가 읽을 수 있는 곳에 있어야 해요. 그래서 지금 저희 회사도 맥락을 최대한 AI가 접근할 수 있는 방향으로 개편하는 중입니다. 앞에서 말씀드린 문서화와 외부 연결이 여기서 다시 중요해지는 거예요.

저희만 그런 건 아니에요. 국내외 다른 회사들도 같은 방향으로 가고 있어서, 공개된 사례 네 가지를 보여 드릴게요.

### #39 사례: 당근

당근 개발팀에는 "이 기능 언제 나갔어요?"라는 질문이 자주 왔다고 해요. 그때마다 개발자가 하던 일을 멈추고 배포 기록을 뒤져야 했고, 답을 기다리는 사람도 같이 멈췄습니다.

글에 이런 문장이 있어요. "배포 내역의 맥락이 개발자 안에만 갇혀 있다는 게, 한 명의 불편이 아니라 팀 전체의 커뮤니케이션 비용을 발생시키는 문제였어요." 앞 장에서 말씀드린 내용과 거의 같죠.

그래서 배포할 때마다 변경 내역을 Notion에 자동으로 쌓고, AI가 그 기록을 기획자나 디자이너도 읽을 수 있는 릴리즈 노트로 매일 풀어 쓰게 했어요. 위클리 미팅 전에 서버 개발자 한 명이 하던 정리는 이 노트로 대신하고, 다른 팀에서도 요청이 와서 주간 요약본까지 만들었다고 해요.

순서도 눈여겨볼 만해요. 글쓴이는 "자산이 먼저 만들어져야 LLM이 일할 수 있다"고 말합니다. AI보다 기록을 쌓는 게 먼저였던 거죠.

### #40 사례: 배달의민족

배달의민족을 만드는 우아한형제들은 사내 지식이 여러 곳에 흩어져 있는 문제가 있었어요. 궁금한 게 생기면 위키, 메신저, 문서함 같은 시스템을 일일이 찾아다녀야 했습니다.

그래서 위키, Jira, Slack, 구글 드라이브를 '물어보새'라는 AI 에이전트 하나에 연결했어요. 지금은 전 직원의 33%가 쓰고 있고, 기사에 따르면 조직별 문의 해결 속도가 평균 21% 빨라졌다고 합니다.

### #41 사례: 토스

토스플레이스 데이터팀은 분석가에게 오는 요청의 70%가 단순한 수치 확인이라는 걸 발견했어요. "지난달 결제 건수 얼마예요?" 같은 질문이요.

흥미로운 건 순서예요. AI를 붙이기 전에 테이블 설명, 용어, 지표 정의부터 AI가 읽을 수 있게 정리했습니다. 그다음 '판다'라는 데이터봇을 만들었어요. 출시 첫 주에 팀원 절반이 썼고, 지금은 70%가 씁니다.

### #42 사례: Uber

해외도 마찬가지예요. Uber에는 엔지니어들이 모여 질문하는 사내 지원 채널이 있는데, 한 달에 약 45,000건의 질문이 올라왔다고 해요. 질문한 사람은 그 주의 담당 엔지니어, 즉 온콜 엔지니어가 답해 줄 때까지 기다려야 했습니다.

그래서 사내 위키, 사내 질문 게시판, 요구사항 문서를 긁어 모아 'Genie'라는 AI 봇에 연결했어요. 지금은 154개 채널에서 7만 건 넘게 답했고, Uber는 엔지니어링 시간 13,000시간을 아꼈다고 추정합니다.

네 회사 모두 AI를 먼저 들인 게 아니라, 사람 머릿속과 여기저기 흩어진 맥락을 AI가 닿는 곳으로 먼저 옮겼어요. 그러고 나니 사람을 거치던 질문이 줄어든 겁니다.

## 내가 AI 쓰는 방법 (약 20분)

### #44 내가 AI 쓰는 방법

후반부에서는 제가 실제로 AI와 어떻게 일하는지 보여 드리겠습니다. 전반부에서 말씀드린 개념이 실제로 어떻게 쓰이는지 찾아보시면서 들어 주세요.

### #45 conductor

제가 매일 쓰는 도구는 conductor예요. 여러 AI 에이전트를 각자 독립된 작업 공간에서 동시에 실행해 줍니다.

작업자 여러 명에게 각자 책상을 주고 한 번에 일을 맡긴다고 생각하시면 돼요. 책상이 따로라서 서로 작업을 망가뜨리지 않습니다. 저는 한쪽에서 기능을 만들게 하고, 다른 쪽에서 버그를 고치게 하고, 저는 결과를 검토하는 역할을 해요.

또 하나 좋은 점은 계획부터 머지까지 한 화면에서 끝난다는 거예요. 가운데에서 에이전트와 대화하고, 오른쪽에서 바뀐 파일을 확인하고, 준비가 되면 바로 머지 버튼을 누릅니다.

### #46 예시 1: 개발 업무의 네 단계

첫 번째 예시는 제 개발 업무 흐름이에요. 대체로 계획하고, 구현하고, 검토하고, 반영합니다. 회사에서 기안을 올리고, 작성하고, 결재받고, 시행하는 흐름과 크게 다르지 않죠.

앞에서 나의 워크플로우를 정의할 때 세 가지를 적으라고 말씀드렸죠. 단계, 입력과 결과물, 완료 기준. 이 네 단계가 첫 번째인 단계예요. 이제 나머지 두 가지를 채워 보겠습니다.

### #47 예시 1: 단계마다 입력·결과물·완료 기준

방금 본 네 단계에 입력·결과물과 완료 기준을 채운 표예요. 한 줄이 한 단계이고, 각 단계가 무엇을 받아서 무엇을 넘기는지, 언제 끝났다고 보는지를 적었습니다.

plan에서는 기획서를 받아 해야 할 일을 쪼개요. pyan-plan이라는 제 지침으로 계획을 세우고, AI가 uiop라는 명령어 도구로 JIRA 티켓을 만듭니다. JIRA는 회사에서 할 일을 관리하는 도구예요. 티켓 하나가 PR 하나가 되고, 티켓 설명이 곧 계획서가 됩니다. 제가 승인해야 다음 단계로 넘어가요.

implement에서는 티켓 하나를 받아 코드를 씁니다. 티켓에 적힌 항목을 다 채우고, lint, 타입 검사, 테스트까지 통과해야 끝이에요. 앞에서 본 결정적 도구가 여기서 완료 기준이 됩니다.

review에서는 lint와 테스트가 먼저 걸러 내고, pyan-review라는 지침으로 AI가 한 번 더 리뷰하고, 마지막으로 제가 직접 봐요.

merge에서는 AI가 커밋 메시지와 PR 설명을 씁니다. PR은 내 코드를 팀 코드에 합쳐 달라는 요청서예요. 동료가 승인하면 제가 머지합니다.

[강조] 굵게 표시한 칸을 보세요. 계획 승인, 최종 검토, 머지 결정. 이 세 곳은 AI에게 맡기지 않아요. AI는 확률로 일하니까, 방향을 정하는 곳과 결과를 받아들이는 곳에는 사람이 서 있어야 합니다. 처음에 말씀드린 빙산 아래의 검증이 바로 이 자리예요.

### #48 예시 2: add-matrix

두 번째 예시는 add-matrix예요. Matrix는 회사에서 쓰는 에러 모니터링 도구입니다. 서비스에서 에러가 나면 기록하고 담당자에게 알림을 보내 줘요.

문제는 새 앱을 만들 때마다 이 설정을 반복해야 한다는 거였어요. 개발, 테스트, 운영처럼 환경이 4개라 앱도 4개를 만들고, 각 환경의 설정 파일을 쓰고, Sentry라는 에러 수집 도구를 연결하고, 알림방과 알림 정책까지 만들어야 합니다. 여러 사내 도구를 오가야 하고, 하나라도 빠뜨리면 에러가 나도 모르고 지나가요.

그래서 이 과정을 스킬로 만들었습니다. SKILL.md에 단계와 순서를 적어 두고, 각 단계는 스크립트가 API를 호출해서 처리해요. 설정 파일을 만든 다음에는 실제 API 응답과 비교해서 제대로 됐는지 검증합니다. 알림방 생성처럼 사람이 직접 해야 하는 일은 AI가 링크와 입력값을 단계별로 안내해 줘요.

결과적으로 대화 한 번이면 설정이 끝나요. 그리고 누가 실행해도 같은 결과가 나옵니다.

여기에는 세 가지 개념이 모두 쓰였어요. 단계와 순서를 적은 SKILL.md는 작업 지침이에요. API 명세처럼 긴 문서는 별도 파일로 빼 두고 필요할 때만 읽게 했으니 맥락 관리이고요. API 호출과 검증을 AI가 매번 새로 짜지 않고 스크립트에 맡겼으니 결정적 도구입니다.

### #49 예시 3: pyan-tldr

세 번째 예시는 정보 수집이에요. 문제는 읽어야 할 정보가 너무 많다는 겁니다. 유튜브 영상, 블로그 글, 아티클이 매일 쏟아지는데 다 볼 수가 없어요.

그래서 이런 흐름을 만들었습니다. 먼저 명령어 도구로 유튜브와 네이버 블로그의 콘텐츠를 가져와요. 그다음 제가 정해 둔 요약 지침으로 핵심만 정리합니다.

결과적으로 30분 동안 훑어봐야 할 정보를 1분 안에 파악하고, 문서로 정리해 둘 수 있게 됐어요.

여기에는 두 가지 개념이 쓰였어요. 요약 형식을 정한 건 작업 지침이고, 콘텐츠를 가져오는 부분은 AI의 기억에 맡기지 않고 도구로 정확히 가져오니까 결정적 도구예요.
